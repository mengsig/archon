**Root cause:** `updatePrice` invalidates only the product cache entry. Category listings are cached separately for 10 minutes and still hold the old price.

**Code path**
- `src/pricing.js:10-11`: `updatePrice` writes the new price to the store, then calls `catalog.cache.delete(productKey(sku))`. It never touches listing entries.
- `src/catalog.js:12-20`: product pages read `product:<sku>`. That key was just deleted, so the next read goes to the store and the product page is correct immediately.
- `src/catalog.js:22-33`: category pages read `listing:<category>:<page>` (keys from `src/keys.js:4`). Each cached row is a copy of `{ sku, name, priceCents }`, so the price is denormalized into the listing.
- `src/config.js:7`: `LISTING_TTL_SECONDS = 600`.

**Why the delay is what it is:** a listing entry is served until it expires, and nothing invalidates it on a price change. The delay is the time left on the listing's TTL, so it can be up to 600 s (10 minutes), depending on when the page was last built. The product TTL is 3600 s, but that doesn't matter here because the product key is deleted on update.

**Why tests didn't catch it:** `test/catalog.test.js:13-18` only checks the product page after an update. There is no test that warms a listing, updates the price, and re-reads the listing.

**Fix options**
1. **Smallest change:** in `updatePrice`, also drop the `listing:<category>:*` entries for the product's category. Use `updated.category` from `store.update`. Because the page count is unknown, add a prefix or predicate delete to `TtlCache`. Scoping to the category keeps the expensive listing rebuilds for other categories.
2. **Structural:** stop storing prices in listing rows. Cache only the SKU order per category and fill prices from the product cache at read time. This removes the duplication that causes the bug.
3. **Versioned keys:** store a version per category in the listing key and bump it on each price update. This is simple, but old entries stay in memory until they expire.

I'd go with option 1, plus a regression test that warms a listing, updates the price, and expects the new price on the next read.

**Assumption:** the cache is in-process (`createCatalog` creates a new `TtlCache`). This fix covers one process. If the service runs as multiple instances, each one keeps its own stale listings, and you would need shared invalidation.
