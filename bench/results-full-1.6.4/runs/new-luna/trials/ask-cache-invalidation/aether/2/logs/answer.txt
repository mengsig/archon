The stale category prices come from the cached listing path in [catalog.js](/home/mengsig/.local/share/archon-bench/f164-kct3x9mo/archon-bench/work/20261120T084524Z/9b9bd6182cb928be0015ba4a/ask-cache-invalidation/src/catalog.js:22). `listing()` caches each category and page under a `listing:<category>:<page>` key. When it builds a listing, it copies `priceCents` into the cached rows, so later store updates don’t change those rows.

`updatePrice()` updates the store and deletes only the product cache entry in [pricing.js](/home/mengsig/.local/share/archon-bench/f164-kct3x9mo/archon-bench/work/20261120T084524Z/9b9bd6182cb928be0015ba4a/ask-cache-invalidation/src/pricing.js:6). That lets `product()` fetch the new price immediately, but leaves all cached category pages untouched. They expire after `LISTING_TTL_SECONDS: 600`—ten minutes—in [config.js](/home/mengsig/.local/share/archon-bench/f164-kct3x9mo/archon-bench/work/20261120T084524Z/9b9bd6182cb928be0015ba4a/ask-cache-invalidation/src/config.js:4).

The fix is to invalidate listing cache entries affected by a price update. Since `updatePrice()` has the SKU but not its category or page keys, it could retrieve the product’s category and delete every cached page for that category, or the cache could track which listing keys contain each SKU. Another option is to avoid caching prices in listing rows and resolve current prices separately when serving them. No code was changed.
