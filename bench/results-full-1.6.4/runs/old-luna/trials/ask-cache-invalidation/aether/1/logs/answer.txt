The stale category price comes from the cached listing path in [`catalog.js`](/home/mengsig/.local/share/archon-bench/f164-p9b3h69d/archon-bench/work/20261120T084439Z/5c61e582f4e809e56239301e/ask-cache-invalidation/src/catalog.js:22). On a cache miss, `listing()` reads the category from the store, selects the page, and caches rows that include `priceCents`. A later request returns those rows until the listing cache entry expires.

`updatePrice()` updates the store and deletes only `product:<sku>` from the cache ([`pricing.js`](/home/mengsig/.local/share/archon-bench/f164-p9b3h69d/archon-bench/work/20261120T084439Z/5c61e582f4e809e56239301e/ask-cache-invalidation/src/pricing.js:6)). That refreshes the product page on its next read, but leaves every cached category page containing that SKU untouched. Those entries expire after 600 seconds—10 minutes—as configured in [`config.js`](/home/mengsig/.local/share/archon-bench/f164-p9b3h69d/archon-bench/work/20261120T084439Z/5c61e582f4e809e56239301e/ask-cache-invalidation/src/config.js:1). So the observed delay is the listing cache’s remaining TTL, up to ten minutes.

The fix is to invalidate the affected listing cache entries when a price changes. With the current key scheme (`listing:<category>:<page>`), `updatePrice()` needs to identify the product’s category and delete all relevant listing-page keys for it. A more scalable alternative is to tag listings by category or version category keys so a price update can invalidate that category’s cached pages together.
