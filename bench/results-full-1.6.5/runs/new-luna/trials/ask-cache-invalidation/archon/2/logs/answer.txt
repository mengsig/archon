The stale category price comes from `Catalog.listing()` in [catalog.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-dwsb1bl5/archon-bench/work/20261125T011222Z/0ac1814a04f63b046bebc1d2/.archon/data/orchestrator/repos/ask-cache-invalidation/src/catalog.js:22). It caches each category and page as a snapshot of `{ sku, name, priceCents }` under a `listing:<category>:<page>` key.

When a merchant changes a price, `updatePrice()` writes the new value to the store and deletes only `product:<sku>` ([pricing.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-dwsb1bl5/archon-bench/work/20261125T011222Z/0ac1814a04f63b046bebc1d2/.archon/data/orchestrator/repos/ask-cache-invalidation/src/pricing.js:6)). Product reads therefore miss their cache and fetch the updated store value immediately. Existing category-listing entries remain cached until expiry.

The listing TTL is 600 seconds—ten minutes ([config.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-dwsb1bl5/archon-bench/work/20261125T011222Z/0ac1814a04f63b046bebc1d2/.archon/data/orchestrator/repos/ask-cache-invalidation/src/config.js:4)). So a price can stay stale for up to the remaining lifetime of the listing entry, roughly ten minutes if it was just populated. On expiry, the next listing request rebuilds it from the updated store.

The fix is to invalidate the affected category listing cache entries when the price changes. Since listing keys include category and page, the update path needs to remove the relevant cached pages for that product’s category. Alternatively, listing reads could resolve prices from the product cache/store, though that changes the listing’s cache strategy. No code was changed.
