The stale category prices come from the separate listing cache. `updatePrice` updates the store and deletes only `product:<sku>` ([pricing.js](/home/mengsig/.local/share/archon-bench/release-167-R4V9TB/r-lzwaa8jj/archon-bench/work/20261128T072020Z/6e2e182bdd43cd3e55898396/.archon/data/orchestrator/repos/ask-cache-invalidation/src/pricing.js:10)). Product-page reads use that product key, so they reload the updated record immediately. Category pages use `listing:<category>:<page>` and cache copied rows containing the price ([catalog.js](/home/mengsig/.local/share/archon-bench/release-167-R4V9TB/r-lzwaa8jj/archon-bench/work/20261128T072020Z/6e2e182bdd43cd3e55898396/.archon/data/orchestrator/repos/ask-cache-invalidation/src/catalog.js:22)).

Those listing entries expire after **600 seconds** ([config.js](/home/mengsig/.local/share/archon-bench/release-167-R4V9TB/r-lzwaa8jj/archon-bench/work/20261128T072020Z/6e2e182bdd43cd3e55898396/.archon/data/orchestrator/repos/ask-cache-invalidation/src/config.js:7)). Because expiry is measured from when each listing was cached, a price change can leave an already-cached page stale for nearly ten minutes.

The fix is to invalidate the affected category’s cached listing pages when a price changes. Since listing keys include both category and page, the code needs a way to remove all relevant pages—for example, track listing keys per category or use a category version in the keys and bump it on price updates. Updating only the product cache, or lowering the listing TTL, would leave the underlying invalidation gap.
