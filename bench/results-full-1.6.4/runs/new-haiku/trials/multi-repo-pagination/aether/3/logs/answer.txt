Added cursor pagination to GET /items in inventory-api and switched inventory-client's listItems to follow next_cursor. Both repos are committed, with clean working trees. Tests pass in both: `python3 -m unittest` (9 tests) and `npm test` (9 tests). I also ran listItems against the real API CLI and it returned all 57 items in order.

inventory-api (commit 117c5d2 "Paginate GET /items with limit and cursor"):
- GET /items takes optional `limit` (1..100, default 20) and `cursor`, and returns {"items": [...], "next_cursor": ...}. next_cursor is null on the last page, including when a page exactly fills the list.
- The cursor is opaque: base64 of the last returned id. The next page starts after that id.
- Invalid limit or cursor returns 400 {"error": "..."}. Digit strings are capped at 3 digits for limit and 18 for the cursor's id, so oversized input can't trigger Python's int-conversion limit.
- README documents the new parameters and response, with a worked example that I verified.

inventory-client (commit 686d27c "Follow next_cursor in listItems"):
- listItems sends no cursor on the first request, then echoes each cursor back unchanged, until next_cursor is null or absent.
- It rejects on a failed page, on a page without an items array, or when the server repeats a cursor, so it can't loop forever.
- Tests cover the multi-page walk, the cursor sequence, absent next_cursor, failures, and the repeat guard.
- README updated.

Choices I made:
- The first request sends only the cursor (no limit), so the API default of 20 applies. Passing limit=100 would cut the number of requests; I didn't, since the spec didn't ask for it.
