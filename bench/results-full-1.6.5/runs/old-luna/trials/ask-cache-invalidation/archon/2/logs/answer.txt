The stale category price comes from the listing cache path in [catalog.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-p5gy6w9p/archon-bench/work/20261125T004922Z/9df65080661abee197248f9b/.archon/data/orchestrator/repos/ask-cache-invalidation/src/catalog.js:23). `listing()` caches each category and page under a `listing:<category>:<page>` key. When a merchant changes a price, `updatePrice()` updates the store and deletes only that product’s cache entry in [pricing.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-p5gy6w9p/archon-bench/work/20261125T004922Z/9df65080661abee197248f9b/.archon/data/orchestrator/repos/ask-cache-invalidation/src/pricing.js:7). It never invalidates the affected listing entries.

The delay is the listing cache’s **600-second (10-minute) TTL**, configured in [config.js](/home/mengsig/.local/share/archon-bench/full-165-Q4J35ZNK/r-p5gy6w9p/archon-bench/work/20261125T004922Z/9df65080661abee197248f9b/.archon/data/orchestrator/repos/ask-cache-invalidation/src/config.js:5). A cached category page keeps its old price until it expires; the next request rebuilds it from the store. Product pages update immediately because `updatePrice()` deletes the product-specific cache key, so the next product read fetches the updated record.

The fix is to invalidate the affected category’s listing cache entries when a price changes—across every page for that category—or use a category-level version in listing keys so updates make old entries unreachable. That requires the update path to know the product’s category (for example, from the updated record). No code was changed.
