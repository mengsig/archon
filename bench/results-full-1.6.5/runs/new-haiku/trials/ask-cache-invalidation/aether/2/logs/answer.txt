The root cause is that a price update invalidates only the product-detail cache entry, not the category-listing entries that also hold the price. I made no code changes; I only read the code and ran a read-only reproduction.

**Code path**

- `updatePrice()` in `src/pricing.js:6-13` writes the new price to the store, then calls `catalog.cache.delete(productKey(sku))`. That removes only the `product:<sku>` key.
- `Catalog.listing()` in `src/catalog.js:22-33` caches the page rows under `listing:<category>:<page>`. Each row embeds `priceCents`.
- Nothing evicts those `listing:` keys on a price change. `updatePrice` doesn't know the page keys, and `TtlCache` has no prefix or category delete.

**Why the delay is about ten minutes**

- `LISTING_TTL_SECONDS` is 600 (`src/config.js:7`), so a listing keeps the old price until its entry expires.
- `PRODUCT_TTL_SECONDS` is 3600, but the product page is correct immediately because its own key is deleted on update.

**Reproduction** (injected clock, no files written)

- After `updatePrice(c, 'A1', 4500)`, `product('A1')` returns 4500.
- `listing('tools')` still returns 5000 at +1 s and +599 s, and returns 4500 at +600 s.

**Suggested fix**

- Preferred: when a price changes, also evict the listing entries that contain the SKU. Look up the product's category and evict that category's listing pages. This needs either a prefix/category delete in `TtlCache`, or a per-category generation counter in the listing key that `updatePrice` bumps.
- Alternative: keep prices out of cached listings and join current prices at read time. This is a bigger change, and it is the right one if listings are cheap to re-price.
- Lowering `LISTING_TTL_SECONDS` only shrinks the window. It does not fix the bug.

**Test gap:** the existing tests (`test/catalog.test.js`) check product freshness after an update but do not check listing freshness, which is why this went unnoticed.
